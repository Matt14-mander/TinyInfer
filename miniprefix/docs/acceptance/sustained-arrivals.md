# MiniPrefix 持续到达基线

测量环境为 Windows、RTX 4070 Laptop GPU（8 GiB，驱动 555.97）、CUDA 12.5.1 和 MSVC 14.29 Release。主扫描 worker 对应 `05c69f7`。GPU 未锁频，四种 prompt 的长度分别为 37、39、43、54 token。这里的容量适用于给定模型、批上限、前缀分布和输出长度。

## 工作负载与计时边界

SmolLM2-135M-Instruct FP32，单个 CUDA worker，最多 4 个并发执行请求，每步预算 32 token、prefill chunk 16、KV 页长 16、共 128 页。四种真实 prompt 轮流到达，每个请求恰好生成 8 个 token。每轮先生成固定到达时间表，每个等宽时间槽内加入带种子的抖动，控制器无需等上个请求完成即可产生下个到达。同步 worker 只能在 STEP 之间接收 SUBMIT，因此所有请求延迟均从**计划到达时间**算起，包含控制器延迟与引擎内排队。

每个速率与缓存模式使用独立进程，先用八请求预热，再清空缓存。关闭模式容量为 0；冷模式以空的 48 条目缓存开始，允许在线学习；热模式提前用相同四种 prompt 完整生成并保留缓存。三种模式在每轮重放相同的到达间隔和 prompt 顺序，轮内打乱各配置的执行顺序。计时区间排除分词、模型加载、预热、prime、统计查询和 Transformers 参考计算。

- 延迟采用客户端收到 token 事件的时刻。TTFT 是首 token 延迟；TPOT 先在单请求内计算七个 token 间隔的均值；E2E 到末 token 为止；ITL 是每一对相邻输出的间隔。
- 延迟分位数合并同配置三轮共 288 个请求，采用 nearest rank。吞吐先按轮计算，再取中位数。指标脚本还提供 p95、提交延迟、排空用时与各轮吞吐范围。
- **到达窗口吞吐**取第 20% 至 80% 到达点之间交付的输出 token/s，测量期间始终有新请求进入。**服务窗口吞吐**取第 20% 至 80% 完成点之间交付的输出 token/s，剔除首尾填充，可包含排空阶段。积压占比是窗口内已到达未完成请求数超过 4 的时间比例。须结合两种窗口和积压占比判断饱和。
- 端到端基线使用原有未插桩 worker；另在相同模型、参数和到达序列下使用启用 `EXEC_TIMING` 的 worker 定位瓶颈。两个二进制、模型、独立参考及 GPU 的指纹保存在各自原始数据头部。

## 饱和吞吐复核

将单轮延长到 512 个请求，持续约 8 s 以 64 请求/s 到达，每种模式独立重复三轮。到达窗口的输入需求为 512 输出 token/s，三种模式的到达与服务窗口均持续积压。表内延迟基于每种模式 1,536 个请求，吞吐为三轮中位数，括号内为到达窗口各轮的最小与最大值。

| 缓存 | 到达窗口饱和吞吐 tok/s | 服务窗口 tok/s | TTFT p50 / p99 (s) | TPOT p50 / p99 (ms) | E2E p99 (s) | 到达结束后排空 (s) |
|---|---:|---:|---:|---:|---:|---:|
| 关闭 | 227.9（195.5–278.0） | 206.5 | 4.86 / 13.41 | 12.3 / 28.4 | 13.50 | 12.03 |
| 冷 | 247.5（211.9–264.9） | 229.8 | 4.49 / 13.14 | 14.9 / 39.6 | 13.36 | 9.98 |
| 热 | 228.1（199.3–234.2） | 219.3 | 5.64 / 12.09 | 16.2 / 45.6 | 12.24 | 11.32 |

该负载在持续到达窗口交付约 228–248 输出 token/s，相当于每秒约 28.5–30.9 个八 token 请求的工作量。冷、热模式每次请求平均复用 42.03、42.25 个 prompt token，关闭时为 0。四种 prompt 很快填热冷缓存，因此预先 prime 主要影响开头的请求。三种模式吞吐范围有重叠，这次数据不足以断言冷或热缓存在饱和吞吐上稳定领先。高载下的秒级 p99 随积压时长增长，应用到线上 SLA 时需要重新给定到达分布、请求长度与允许排队时间。[长窗口原始样本](sustained-capacity.jsonl.gz)

## 瓶颈与调度重叠决策

在 96 请求/s 下独立执行每种模式三轮，计时在预热和 prime 之后开启。下表分母是控制器等待所有 STEP 的累计墙钟时间，包含 worker IPC、事件编码与 Python 解析。准入和计划列从 Engine 检查可用槽位计到生成有序计划，含容量预约。批次打包、采样、发布、清理与 IPC 在此列之外。

| 缓存 | 准入和计划 | forward 至 logits 回传完成 | 主机调用 forward | CUDA stream 中的 forward |
|---|---:|---:|---:|---:|
| 关闭 | 0.028% | 85.9% | 74.3% | 83.3% |
| 冷 | 0.024% | 86.3% | 68.7% | 83.9% |
| 热 | 0.027% | 86.7% | 65.5% | 84.0% |

这三组计时轮次中，STEP 合计占从首个计划时间槽到最后一个 token 的 99.1%–99.2%。正式延迟表使用关闭插桩的原始 worker；独立轮次与正式扫描的绝对速度有波动，计时轮次仅用于估计步骤内部占比。CPU/CUDA 均以 Release 从头构建，CTest 分别通过 56/56、65/65，Python 回归通过 19/19。

**当前优先优化 CUDA forward 路径，暂缓调度与 CUDA 执行重叠。** 即使完全隐藏准入与生成有序计划的时间，按本次测量也只能节省不到 0.03% 的 STEP 时间。将打包等工作一并提前，其理论空间受 forward/回传以外的约 13–14% 限制；这部分还包含依赖当前 logits 的采样、发布和事件交付。单独异步接收新请求可能减少提交延迟，而过载时仅靠提前接收无法消除持续增长的队列。

主机调用 forward 的时间与 CUDA event 所测 stream 区间重叠，上表各列不能相加。stream 区间包含 kernel 间等待，主机调用也可能等待驱动；这些数据可将瓶颈定位到模型执行路径，无法据此区分 GPU 算术、访存与启动间隙。下一步应检查 kernel 时间线，并单独对照设备端 greedy 采样：本次扫描在 96 请求/s 下，每 96 请求回传约 144–188 MiB logits。比较仅回传 token ID 时的 TPOT 和饱和吞吐，可检验回传与主机扫描是否值得优化。

## 复现

```text
python miniprefix/benchmarks/sustained.py --worker CUDA_WORKER --model-dir MODEL_DIR --output arrivals.jsonl.gz
python miniprefix/benchmarks/sustained.py --worker CUDA_WORKER --model-dir MODEL_DIR --rates 64 --requests 512 --output capacity.jsonl.gz
python miniprefix/benchmarks/sustained.py --worker PROFILE_CAPABLE_CUDA_WORKER --model-dir MODEL_DIR --rates 96 --profile --output profile.jsonl.gz
python miniprefix/benchmarks/sustained.py --summarize arrivals.jsonl.gz
python miniprefix/benchmarks/sustained.py --summarize capacity.jsonl.gz
python miniprefix/benchmarks/sustained.py --summarize profile.jsonl.gz
```

每次运行验证所有生成 token 与独立 Transformers FP32 full-prefix greedy 参考相符，并检查实际 forward 与跳过的前缀长度、权重与 KV 常驻、请求及前缀引用释放。原始记录包含每请求到达、提交、逐 token 交付时刻、输出 ID、完成原因、每步起止时间和计数器差值。[负载扫描](sustained-arrivals.jsonl.gz) · [独立计时轮次](sustained-profile.jsonl.gz)
