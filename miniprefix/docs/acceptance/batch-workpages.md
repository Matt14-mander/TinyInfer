# 批量物理页准备验收（2026-11-24）

基于测量与压力验收提交 `ee19282` 的未提交实现。改动集中于 KVManager 的整批空间预检和缓存 LRU 只读引用快照；未增加 KV 池容量、抢占、异步调度或新 CUDA kernel。

## 实现与语义

先验证全部输入/预约，再模拟按 LRU 去除缓存引用后，空闲页能否覆盖所有扩页和同时存活的 COW 目标。固定引用不计作可回收页；同页多个缓存引用需逐个扣除；尾页变独占可取消 COW。计划不足直接回退且不驱逐。完整计划成功后按原 LRU 策略准备页面，GPU 启动前整批页面已由事务持有。

Engine 发布调用顺序保持原样，不提前发布未来行或跨过未 resident 请求的恢复边界。批次边界的驱逐时点、次数和最终命中统计可与旧串行回退路径不同。进入准备后的失败回滚恢复请求映射/已提交长度、释放工作页；已执行的驱逐效果保留，沿用普通 append 的约定。详细设计见 [批量物理页准备](../batch_workpages.md)。

## 同机修改前/后比较

RTX 4070 Laptop 8 GiB，SmolLM2-135M FP32。沿用 capacity 基线：共享准入、20 页物理池、20 页缓存（off 为 0）、页长 8、batch 4、token budget 32、chunk 16。四种合成 prompt 长度为 65/68/71/74，公共前缀 64 token，输出各 8 token。40 请求/s，每配置三轮 × 128 请求，按轮打乱 before/after 和缓存模式，配对使用同一到达 seed。18 个案例、2,304 请求全部通过逐 token 参考及资源清理检查。

TTFT/E2E 从计划到达计时，包含提交延迟与排队；TPOT 是请求内输出间隔均值。原生测量包含主机观测，不包含 tokenizer/worker IPC。加载、参考、预热及 prime 排除。下表是各轮分位数/吞吐的中位数，延迟单位 ms；范围为三轮服务窗口吞吐最小至最大。未锁频，不作显著性推断。

prefill/mixed 回退在这组负载的所有配置中均为 0。固定物理池峰值仍为 20 页，没有通过隐式增加 KV 页数获得收益。

冷/热缓存的 decode 回退在修改后三轮均为 0；服务吞吐由约 160/154 提高至约 320/319 token/s。关闭缓存的批量次数不变、吞吐范围重叠，因此不声称 off 模式有性能提升。

修改后的冷/热吞吐已接近 40×8=320 token/s 的输入需求，不能把该值作为新的饱和吞吐上限。TTFT 从秒级降到几十毫秒主要因为同一到达率下不再持续积压，不能解释为单请求 prefill kernel 加速了相同比例。

存在缓存复用代价：每轮热缓存复用 token 中位数从 8,750 降到 8,443，forward token 从 1,042 升到 1,349。整批空间准备可能提前驱逐更多旧引用，但本负载中批量执行收益超过了额外计算。不同前缀分布、页池和到达率仍需复测。

首次修改前基线进程超时，未产生有效样本；之后先做短程复现，再重跑完整 18 案例矩阵。这里没有选择性删除矩阵内的慢样本。修改前/后可执行文件与模型 SHA256 均记录在原始数据头部及汇总中。
