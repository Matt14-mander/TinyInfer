# 精确前缀缓存真实收益：CUDA FP32，2026-10-26

真实 SmolLM2-135M-Instruct、RTX 4070 Laptop 的固定八请求流，off/cold/warm 各五个独立进程。
**共享负载观察到实际计算节省和端到端收益；TPOT 没有明确改善，零共享不应解读为缓存加速。**
主实验只测 CUDA；CPU 仅用于独立数值 oracle，不提供 CPU runner 性能结论。

## 固定范围与验收

- 3 组负载×3 模式×5 轮，共 45 个独立 worker、360 个完成请求、2,880 个计时窗口输出 token。
- 同一组请求的 off/cold/warm 输出全部匹配独立 Transformers CPU FP32 eager full-prefix Greedy；16 个唯一 prompt 在计时前准备 oracle。
- FP32，context 256、活跃上限 2、token budget 32、chunk 16、页长 16、pool 128、cache 48；没有跨请求矩阵 batching。
- 每请求 120 prompt token（96-token 根+24-token 问题）和固定 8 输出 token，EOS 关闭；到达 0/0/25/25/50/50/75/75 ms。
- raw tokenized 英文段落/问题使用固定 token 长度，不套用 chat template，不评价回答质量。源文本和全部 token 入档。
- cold 指流开始时缓存为空，允许流内学习/命中；warm 只预存共同的六页根，不预存八条实际问题。
- 相同负载内模式顺序随轮次轮换，负载顺序也轮换，全部串行。每个 worker 三次 warmup，均在窗口外。

详细定义和命令见 [测量协议](../prefix_benefit.md)。以下单项为五轮中位数，方括号为 min/max。

表中是五个此值的中位数，不代表生产尾延迟/SLA。tokenizer、oracle、启动、warmup、seed、stats、clear 和写盘在主窗口外。

## 同轮配对收益与 seed 成本

下表先计算每轮 on/off 的比值，再汇总五轮；不是上表两个中位数相除。
速度比大于 1 为收益；prime-inclusive 将 warm 的 97-token seed 实际执行成本加回分母，
分子仍只有主流的 64 个输出 token，不计 seed 的一个输出。off/cold 的人工预热 seed 不作为应用成本。

|---|---|---:|---:|---:|
| 共享 96 token | cold | 1.305× [0.814, 2.044] | 1.430× [1.194, 1.657] | 1.430× [1.194, 1.657] |
| 共享 96 token | warm | 1.758× [1.618, 3.086] | 1.625× [1.534, 1.877] | 1.518× [1.415, 1.671] |
| 半数共享 | cold | 1.413× [0.852, 1.816] | 1.080× [0.928, 1.257] | 1.080× [0.928, 1.257] |
| 半数共享 | warm | 2.234× [1.670, 2.594] | 1.332× [1.134, 1.588] | 1.269× [1.080, 1.485] |
| 无共享 | cold | 1.031× [0.844, 1.282] | 1.042× [0.895, 1.089] | 1.042× [0.895, 1.089] |
| 无共享 | warm | 0.995× [0.699, 1.276] | 1.018× [0.804, 1.344] | 0.960× [0.731, 1.260] |

共享热缓存的 seed 中位数 65.86 ms，计入成本后的绝对吞吐中位数 68.57 token/s；
半数共享分别为 56.08 ms 与 56.49 token/s。
startup、权重上传和其余预热仍在这些值之外。这是八条请求承担一次 seed 成本的摊销，不是完整进程冷启动收益。

所有高共享 warm/cold 轮次的吞吐均高于同轮 off；但高共享 cold 的第一轮 TTFT P50 反而更慢（0.814×）。
半数共享 warm 的五轮吞吐均提升，cold 第一轮吞吐为 0.928×，不能声称 cold 在所有指标和每轮都加速。
warm 的 TPOT on/off 配对中位数：全共享 1.028、半数共享 0.972，未证明 decode 延迟改善。
缓存减少的是 prompt forward；每组仍有 56 个生成 token 再输入模型。

## 计算量、命中与缓存占用

| 负载 | 模式 | 请求命中 | 跳过 prompt token | 实际 forward token | 保留缓存 MiB | 淘汰次数 |
|---|---|---:|---:|---:|---:|---:|
| 共享 96 token | off | 0% | 0 | 1016 | 0.00 | 0 |
| 共享 96 token | cold | 75% | 576 | 440 | 9.84 | 0 |
| 共享 96 token | warm | 100% | 768 | 248 | 9.84 | 0 |
| 半数共享 | off | 0% | 0 | 1016 | 0.00 | 0 |
| 半数共享 | cold | 25% | 192 | 824 | 26.72 | 0 |
| 半数共享 | warm | 50% | 384 | 632 | 26.72 | 0 |
| 无共享 | off | 0% | 0 | 1016 | 0.00 | 0 |
| 无共享 | cold | 0% | 0 | 1016 | 33.75 | 8 |
| 无共享 | warm | 0% | 0 | 1016 | 33.75 | 14 |

- 全部关闭缓存样本实际计算 8×(120+7)=1,016 token。全共享 cold 跳过 576、warm 跳过 768；热缓存实际计算 248，减少约 75.6%。
- 全共享 cold 的前两个活跃请求都未命中，随后六个命中；半数共享 cold 仅后两个共享请求命中。冷缓存流内有真实收益，不等于每条请求都冷。
- CUDA token H2D 为 actual forward×4：关闭 4,064 字节、全共享 cold 1,760、warm 992；KV/权重 H2D 全部零增量。
- 每组仅 8 次新设备分配（序列页表），workspace/pool 不增长；全部请求结束时 live 页只有缓存引用，设备页表为零，clear 后所有 live KV 归零。
- 物理池始终预留 90 MiB；48-page cache 容量最多占用其中 33.75 MiB。上述保留量不是额外 cudaMalloc，也不是显存总量节省。
- 缓存字节只含 GPU K/V payload，不含主机 vector/map key 和 cuBLAS/驱动内部开销；进程峰值计数包括 warmup/seed，不冒充测量窗口峰值。

## 零共享控制与解释限制

零共享的 forward 始终为 1,016、复用为零。warm/off 吞吐比范围 0.804–1.344，cold/off 为 0.895–1.089；
两个方向都出现，不能把表中微小中位数上涨归因于缓存收益，也不能从本实验孤立估算索引开销。
无效 warm seed 额外保留空间且付出预填充成本；计入 seed 的配对吞吐中位数为 0.960×。
因此保留默认关闭/显式容量配置的行为合理，本数据不支持对未知共享率无条件开启缓存。

主机为 Windows 11 build 26200、Python 3.12.3；RTX 4070 Laptop 8188 MiB、驱动 555.97。
GPU 前后快照温度 61→65°C，未锁频或隔离桌面；没有逐轮/运行中频率轨迹，不能排除系统调度、
功率与频率变化。完整 min/max、标准差、全部配对与原始样本保留，不做显著性或置信区间宣称。
本次是本机短流、固定长度与三种共享构造；不覆盖长时间饱和、长上下文、多租户、COW、
抢占、多 GPU 或 HTTP/text gateway。收益包含少做 prefill、少走步骤和少传 logits 的综合效果，不是 kernel-only speedup。
